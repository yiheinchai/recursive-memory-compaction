Watch one lesson get shorter

That is the whole idea.

A lesson only gets shorter after it has been loaded, actually used, and the work succeeded — which is proof it contained slack. The candidate has to reproduce real past work before it is allowed to replace anything.

And nothing is thrown away. L0 stays underneath, and L2 records exactly which claims it dropped, so any of them can be pulled back.

Where a lesson comes from — one session, then the next

You never write one.

You spend a session getting something right — a wrong turn, a correction, a fix. RMC watches that happen and writes down the conclusion, not the transcript. Next time the same problem comes up, the conclusion goes into context and the session does not.

The same thing, across a whole store

Now do that to a whole store.

Lessons kept never falls. Nothing is ever deleted — the verbose original of every lesson stays reachable at the bottom of the tree forever.

Tokens loaded per prompt falls, because recall only reads the top row. Every other system moves these two numbers together. Pulling them apart is the entire point.

Why it's different

There were only two options.
Both of them rot.

Append-only stores keep everything and grow until retrieval is guesswork and the context bill dwarfs the task it was meant to help with.

Summarisers stay cheap by throwing things away, and what they throw away first is the exact port, the one flag that mattered. The loss is invisible until something breaks.

What makes it work

Three ideas, and none of them is a similarity score.

01

Use is the signal

Not age, not size, not a schedule. A lesson earns a shorter form only when it was loaded, actually used, and the work succeeded — which is proof it contained slack. Served but ignored earns nothing.

02

Nothing is deleted

Compression adds a level above. The verbose original sits underneath it forever, so "shorter" is never a bet you can lose. The worst case is that you walk back down.

03

Every loss is on the record

A shorter lesson must declare exactly what it dropped, as discrete claims. That turns walking back down from a search into a lookup — and it is why the short form is safe to load first.

The hard part

What happens when the short lesson isn't enough?

This is the question that sinks most compression schemes. Compression normally destroys the very information you would need to invert it, so recovering the right detail becomes a blind walk down a tree.

RMC makes recording the loss mandatory. Every compressed lesson carries a manifest of the claims it removed and which node still holds each one — so "which detail do I need back?" is a short ranked list, not an exploration.

Install

You don't drive it.

Install once, then work normally. RMC runs in hooks: it injects on prompt submit, reflects off-thread when a turn ends, mints and compresses when a session ends, and consolidates once a day. Every expensive step is detached, so nothing blocks your turn.

Python 3.10+, at least one of claude or codex, and zero third-party Python dependencies. The store is plain files in your repo — nothing is sent anywhere.

As a Claude Code plugin
/plugin marketplace add yiheinchai/rmc
/plugin install rmc@rmc
Or from a clone
git clone https://github.com/yiheinchai/rmc
cd rmc && ./bin/rmc install \
  --target claude --target codex
Then, whenever you're curious
rmc status     # what it knows, what it cost
rmc tree       # the graph, by level
rmc recall --prompt "..."  # what it would inject
